# store

Creates a root Store. Atoms and selectors are definitions that hold no value;
a Store holds their values for itself and its [scopes](#scopes), and is where
you read, write, and subscribe.

## Usage

```ts
import { atom, store } from "valdres"

const myStore = store()
const countAtom = atom(0)
```

`store()` takes no arguments and throws a `TypeError` if given any. A Store has
no `id` and no options; keep a reference to the Store you need, or pass it to a
framework [Provider](/react/Provider).

| Method                           | Does                                                                   |
| -------------------------------- | ---------------------------------------------------------------------- |
| `get(state)`                     | Read the committed value of an Atom, Selector, or collection           |
| `set(atom, value)`               | Store `value`                                                          |
| `update(atom, updater)`          | Store `updater(current)`                                               |
| `reset(atom)`                    | Remove this Store's own value                                          |
| `delete(row)`                    | Remove a [collection](/valdres/collection) row                         |
| `sub(state, callback)`           | Subscribe; returns an unsubscribe function                             |
| `sub(state, { settle, notify })` | Subscribe with [phase-keyed handlers](#writing-during-a-change-settle) |
| `txn(callback)`                  | Run an atomic [transaction](#transactions)                             |
| `scope(name?)`                   | Get a named child Store, or create an anonymous one                    |
| `dispose()`                      | Terminate this Store and its scopes                                    |

The Store facade exposes operations, not its mutable graph/cache runtime.
Framework and tooling integrations use Valdres' versioned adapter entrypoint
instead of reaching through the public Store object.

<div className="callout callout-note">
    <div className="callout-title">Upgrading from earlier betas</div>
    The 1.0 Store does not have `store(id, options)`, `store.id`,
    `StoreOptions` (`batchUpdates`, `enumerable`, `schemaValidation`),
    `snapshot`, `hasScope`, `detach`, `onDispose`, `unset`, `unsetAll`, `del`,
    the callback form of `store.scope(name, callback)`, or a shared
    `globalStore`. `set` no longer calls updater functions (use `update`), and
    writes no longer return a value or accept Promises.
</div>

## Reading state

```ts
myStore.get(countAtom) // 0
```

`get` returns the stored reference. Atom values and selector results are shared
by reference with every reader; Valdres does not copy or freeze them. Treat them
as read-only and write a new value to change state.

## Writing state

```ts
myStore.set(countAtom, 42) // stores 42
myStore.update(countAtom, prev => prev + 1) // stores 43
myStore.reset(countAtom) // back to the atom's initial value, 0
```

`set` stores the value it is given and never calls it. `update` calls its
updater with the current value and stores the result. TypeScript rejects
`set(countAtom, prev => prev + 1)` for an Atom whose value is not a function.

Function-valued atoms are ordinary values, so `set` stores the function:

```ts
const onSaveAtom = atom<() => void>(() => {})

myStore.set(onSaveAtom, () => console.log("saved"))
myStore.get(onSaveAtom)() // logs "saved"
```

Writes return `undefined`. Values and updater results must be synchronous: a
Promise or other thenable throws `InvalidSynchronousAtomValueError`. Await the
work first, then write its result.

In a [scope](#scopes), `reset` removes the scope's own value, and the Atom reads
its parent's value again.

## Collection rows

A [collection](/valdres/collection) is a readonly membership State whose
callable handle returns readonly rows. Read rows with `get` and mutate them with
the Store's row overloads:

```ts
import { collection, store } from "valdres"

type Todo = { title: string; done: boolean }

const todos = collection<string, Todo>()
const milk = todos("milk")
const app = store()

app.get(milk) // undefined
app.set(milk, { title: "Buy milk", done: false }) // insert
app.update(milk, current => ({ ...current, done: true }))
app.get(todos) // [milk]
app.delete(milk) // locally absent
app.get(milk) // undefined
app.set(milk, { title: "Buy milk again", done: false }) // reinsert
app.reset(milk) // remove the root's local value
```

`set(row, value)` is an upsert. `update(row, updater)` requires an effectively
present row and otherwise throws `MissingCollectionRowError`. Row values and
updater results must be synchronous and cannot be `undefined`, which represents
absence. Use `set` for function values; only `update` invokes its function.

In a child scope, `delete(row)` installs a local absence that hides an inherited
parent value. `reset(row)` removes either a local value or that deletion, then
reconnects the row to its parent:

```ts
app.set(milk, { title: "Buy milk", done: false })
const draft = app.scope("draft")

draft.delete(milk)
draft.get(milk) // undefined

draft.reset(milk)
draft.get(milk) // { title: "Buy milk", done: false }
```

The collection, each row, and [presence(row)](/valdres/presence) all work with
`get`, `sub`, and selectors. Looking up or reading a row does not insert it.

## Subscribing to changes

Subscription callbacks are notifications. Read the current value from the store
when the callback runs:

```ts
const unsub = myStore.sub(countAtom, () => {
    console.log("count changed:", myStore.get(countAtom))
})

// Later: stop listening
unsub()
```

A callback runs after the update has committed. It may read committed state
with `get`, on this or any other Store, and it may unsubscribe. One read is not
allowed: sampling an `externalAtom` that has no subscriber, directly or through
a selector, throws `DormantExternalReadError`. Subscribe to that State first, or
read it outside the callback. A callback cannot change state either: calling
`set`, `update`, `reset`, `delete`, `txn`, `sub`, `scope`, or `dispose` on any
Store, or creating a Store, throws `CallbackCapabilityError`.

To write in response to a change, either:

- pass a [`settle` handler](#writing-during-a-change-settle), whose writes
  become part of the same update, or
- schedule a new operation:

```ts
myStore.sub(countAtom, () => {
    const count = myStore.get(countAtom)
    queueMicrotask(() => myStore.set(lastSeenAtom, count))
})
```

Deferred work is a separate operation, not part of the original atomic update.
Subscribers have already been notified of the first write; the second commits
and notifies on its own, and can fail on its own.

### Notification failures

When a subscriber throws, the update has already committed. The remaining
subscribers still run, then the call that caused the update (`set`, `update`,
`txn`, …) throws a `SubscriberNotificationError`. Its `committed` property is
`true`, `cause` is the first failure, and `causes` lists all of them.

Do not retry the original write when you catch it; that would apply it twice:

```ts
import { SubscriberNotificationError } from "valdres"

try {
    myStore.update(countAtom, n => n + 1)
} catch (error) {
    if (!(error instanceof SubscriberNotificationError)) throw error
    // The increment committed. Report the subscriber failure, don't retry.
    reportError(error.cause)
}
```

## Transactions

`txn` stages several writes and commits them together. Subscribers are notified
once, after the commit, and never see the intermediate states:

```ts
myStore.txn(tx => {
    tx.set(atomA, 1)
    tx.update(atomB, n => n + 1)
})
```

The callback receives a transaction cursor with `get`, `set`, `update`,
`reset`, `delete`, `scope`, and the experimental
[`resetAll`](#resetting-a-scope-resetall). Its reads include the writes
staged so far. The cursor's methods can be destructured:
`myStore.txn(({ get, set }) => …)`.

The transaction exposes the same collection-row operations, and any error
aborts Atom and row writes together:

```ts
const active = todos("active")
const inherited = todos("inherited")
app.set(inherited, { title: "Inherited", done: false })
const draft = app.scope("transaction-draft")

draft.txn(txn => {
    txn.set(active, { title: "Active", done: false })
    txn.update(active, current => ({ ...current, done: true }))
    txn.delete(inherited)
    txn.reset(inherited)

    txn.get(active) // includes the staged update
    txn.get(todos) // includes staged membership
})
```

Valdres owns commit and rollback: a successful callback commits once, while a
callback that throws discards every staged write. Callback transactions
intentionally expose no manual `commit()` or backing store `data`.

The transaction hands back whatever the callback returned, so a value read
against its view can come straight out. If a subscriber then fails, `txn`
throws a [`SubscriberNotificationError`](#notification-failures) instead and the
return value is lost, although the writes committed:

```ts
const total = myStore.txn(txn => {
    txn.set(priceAtom, 100)
    return txn.get(priceAtom) * quantity
})
```

A callback that returns a Promise or other thenable throws
`InvalidTransactionCallbackResultError` and commits nothing. A transaction
commits synchronously, so it cannot await anything.

### Use the cursor, not captured Stores

While a transaction callback runs, Store operations captured from outside it
throw `TransactionPhaseError`. That includes `get` on the same Store, its
scopes, unrelated Stores in other trees, nested `txn` calls, `sub`, and
`store()`. Do all Store work through the cursor:

```ts
myStore.txn(tx => {
    const count = tx.get(countAtom) // not myStore.get(countAtom)
    tx.scope("draft").set(countAtom, count) // a scope of the same tree
})
```

`tx.scope(nameOrStore)` reaches a scope in the transaction's own tree.
`tx.scope(name, scoped => …)` runs a callback against it and returns its
result. A missing named scope throws `ScopeNotFoundError`, and a Store from a
different tree throws `StoreTreeMismatchError`. The cursor closes when the
callback returns; using it afterwards throws `TransactionClosedError`.

## Resetting a scope: `resetAll`

<div className="callout callout-note">
    <div className="callout-title">Experimental</div>
    `resetAll` is experimental during the beta.
</div>

`tx.scope(child).resetAll()` discards everything a child scope owns in one
step: every atom and family member it set, and every collection row it set or
deleted, including writes staged earlier in the same transaction. The scope then
reads as an untouched child of its parent, including collection order:

```ts
const movies = collection<string, string>()
const root = store()
for (const key of ["a", "b", "c", "d"]) root.set(movies(key), key)

const draft = root.scope("draft")
draft.delete(movies("b"))
draft.get(movies) // a, c, d

root.txn(tx => tx.scope(draft).resetAll())
draft.get(movies) // a, b, c, d: the parent's order
```

Resetting the same rows one at a time with `reset` reveals `b` at the end
(`a, c, d, b`), because each reveal is a new placement. `resetAll` restores
the parent's order instead.

The scope itself stays: its handle, its subscriptions, and its descendant scopes
remain. That makes it the way to rebuild a draft in place. Clear it and
write its new contents in the same transaction, and subscribers see one change
from the old contents to the new:

```ts
root.txn(tx => {
    const cursor = tx.scope(draft)
    cursor.resetAll()
    for (const [key, value] of snapshot) cursor.set(movies(key), value)
})
```

- **Child cursors only.** `resetAll` exists only on transaction cursors;
  there is no `Store.resetAll`. It takes no arguments. On the transaction's
  root cursor, or with an argument, it throws `TypeError` and stages nothing.
  The other cursor rules apply too: after the callback returns it throws
  `TransactionClosedError`.
- **All or nothing.** Every atom is resolved before anything is staged. If one
  fails, for example a lazy atom whose initializer throws when the scope falls
  back to it, `resetAll` throws and stages nothing. Its resets are ordinary
  staged writes: an error escaping the callback discards them with the rest,
  and writes made after it in the same transaction apply on top.
- **Values and notifications.** Each state then reads the parent's value as of
  the end of the transaction, unless the transaction writes it again. Equality
  and notification work exactly as for `reset`: a subscriber is notified once
  if its value changed by `Object.is`, and an atom's custom `equal` is not
  consulted. A scope that is otherwise untouched and aligned with its parent
  serves unchanged results, so resetting it publishes nothing. Having no row
  overrides is not enough: a scope can still keep an order of its own from
  earlier writes (for example a row deleted and then reset), and restoring
  that order publishes membership and query changes. A reset that changes
  nothing may still do transaction bookkeeping.
- **Order.** In every collection, whether or not the scope owned rows there,
  membership becomes what an untouched child of the parent reads: the parent's
  order, followed by rows that became present later in the same transaction, in
  the order those writes happened. Writes to the scope after the reset order
  as they would in that untouched child. `reset(row)` keeps its own behavior.
- **Descendants.** Descendant scopes keep their own values: a descendant that
  inherits a reset atom is notified once if its value changes, and a
  descendant's own override is untouched and not notified. A descendant keeps
  following the restored order if, before the transaction, it showed the same
  rows in the same order as the scope, it writes no rows of that collection in
  the transaction, and its own rows agree with the restored ones. Any other
  descendant keeps its own order and adds the rows the reset reveals after its
  existing rows, in the parent's order. `resetAll` never clears descendants
  and never moves a scope to another parent.
- **The current parent.** The scope inherits the parent's state as it is in
  this transaction, not as it was when the scope was first written. Rows the
  parent has gained since become visible. To hide one, `delete` it in the scope
  after the reset.
- **`settle`.** `settle` handlers whose triggers change run after the commit,
  as for any update. They see the reset state and may write the scope again. A
  `settle` handler registered on a child scope can call `tx.resetAll()` on
  its own cursor.
- **Errors after the commit.** If `txn` throws after the commit applied, the
  reset stays applied. That includes a `SubscriberNotificationError` (always
  `committed: true`) and other failures surfacing after apply, such as a
  `RuntimeMismatchError`. Only an error before the commit, inside the callback
  or while staging, discards the reset.
- **Cost.** Valdres gives no linear complexity or latency bound for
  `resetAll`. It scans what the scope owns, restores order, and does
  bookkeeping. A cold membership read inside the transaction, below nested
  reset or mirroring scopes, can do comparison work on the order of the
  collection size times the depth squared, in addition to those scans and that
  bookkeeping. Warm reads are memoized and skip that search, until a write that
  affects the collection makes the next read cold again. Supporting
  `resetAll` also adds small costs elsewhere: ordinary child-scope transactions
  do conditional bookkeeping to record when a scope's order becomes its own,
  and plain Stores run an inspection check on restored memberships without
  allocating inspection details.

## Writing during a change: `settle`

<div className="callout callout-note">
    <div className="callout-title">Experimental</div>
    The `settle` handler is experimental during the beta.
</div>

`sub` also takes phase-keyed handlers. `settle` runs inside the update, while
state is still settling, and may write. `notify` runs after it settles, exactly
like the callback form:

```ts
const saving = atom(false)
const saveRequest = atom<{ seq: number } | null>(null)

const stop = myStore.sub(hotkeyMatch, {
    settle: tx => {
        const match = tx.get(hotkeyMatch)
        if (match.command !== "save") return
        tx.set(saving, true)
        tx.set(saveRequest, { seq: match.seq })
    },
    notify: () => announce(myStore.get(saving)),
})

// Later: removes both handlers. Calling it again does nothing.
stop()
```

Use `settle` for commands whose result must appear together with the input that
caused it, such as a keyboard shortcut that sets a flag. Pass either handler or
both; any other key throws.

`notify` is not an on-success callback for `settle`. It observes the final state
of every update that changes the trigger, so it also runs when its `settle`
threw and wrote nothing. It can also run while subscribing, when attaching an
external source changes its value; `settle` never runs then.

- **Explicit trigger.** `settle` runs when the served value of the State you
  pass changes. Reads through `tx.get` do not add triggers.
- **No initial run.** Subscribing never runs `settle`, not even when it attaches
  an external source whose value then changes. Only later changes do.
- **Latest state.** No triggering value is passed. `tx.get` reads the latest
  committed state, including commits of `settle` handlers that ran earlier in
  the same update, plus the handler's own staged writes. An earlier handler can
  therefore change whether a later one is still eligible, and among handlers
  that are eligible when their turn comes, registration order decides which runs
  first. Recording that an input was handled, in the same transaction as the
  command's writes, stops later handlers from also succeeding for it; it does
  not freeze eligibility or pick a winner. When a decision must reflect the
  moment the input happened, make it once and store it explicitly.
- **One publication.** Each `settle` call is its own synchronous transaction.
  Its commit updates selectors immediately, and may trigger further `settle`
  handlers in a following round. Subscribers, including `notify` handlers and
  React components, are notified once, after the last round, and only ever see
  the final state.
- **Order.** `settle` handlers run in the order their triggers changed, then in
  registration order. One whose trigger changes again after it has run runs
  again in the next round. At most 64 rounds run. Then the write that started
  the update throws a `SubscriberNotificationError` (`committed: true`) with a
  `SettleLimitError` cause; commits from the rounds that ran stay applied.
- **Failure isolation.** A `settle` handler that throws, or returns a promise,
  discards its own staged writes. Other handlers still run, and earlier commits
  stay. Failures are reported after subscribers run, as causes of a
  `SubscriberNotificationError`. A failure after its writes were applied does
  not undo them; derived state still updates before subscribers are notified. If
  recomputing a selector fails at that point, the selector serves that failure
  as its error, and its dependents fail with it, until one of its inputs
  changes. Subscribers never see a value computed before the write.

`settle` is not a database transaction around the whole update. It cannot undo
work outside Valdres. Keep I/O, DOM work, and anything that can synchronously
re-enter an external source (`focus()`, dispatching events) out of `settle`. Do
that work in `notify`, or any ordinary subscriber, which runs after the one
publication, and report completion as a separate operation:

```ts
myStore.sub(saveRequest, () => {
    const request = myStore.get(saveRequest)
    if (request === null) return
    api.save(myStore.get(documentAtom)).then(
        () =>
            myStore.txn(tx => {
                tx.set(saving, false)
                tx.set(saveRequest, null)
            }),
        error =>
            myStore.txn(tx => {
                tx.set(saving, false)
                tx.set(saveRequest, null)
                tx.set(saveError, error)
            }),
    )
})
```

Work that needs a newly rendered DOM node belongs after the framework's own
commit. Notification alone does not mean the DOM is ready. Cancelling the live
native event (`event.preventDefault()`) is safe inside `settle` because it runs
synchronously while the event dispatches.

A `settle` handler belongs to the store, or scope, it was registered on. Like
any transaction, it reaches other scopes of its tree only through `tx.scope`,
and cannot write a Store in another tree. The two phases differ in what they
may do:

|                    | `notify` (or a plain callback)                                | `settle`                                     |
| ------------------ | ------------------------------------------------------------- | -------------------------------------------- |
| Runs               | after the update settles, once                                | during the update, before any `notify`       |
| Can write state    | no                                                            | yes, through its transaction                 |
| Reads              | `store.get` of committed state, except dormant external atoms | `tx.get` of the latest state plus its writes |
| Unsubscribe inside | allowed                                                       | not allowed                                  |

The guarantee holds per update and per store. Two external sources that are
invalidated one after the other for the same DOM event produce two updates.

## Scopes

`scope(name)` returns a child Store that reads through to its parent and keeps
its own writes local — see the [scoped stores guide](/guides/scoped-stores).

- **Named scopes are shared.** While a named scope is alive, every
  `scope(name)` call on the same parent returns the same handle. Names are per
  parent.
- **`dispose()` ends it for everyone.** Disposing a named scope terminates it
  for every holder of that handle. The next `scope(name)` creates a new scope
  with no local state.
- **`scope()` without a name** creates a new anonymous child on every call.
  Use it for isolation that one consumer owns and disposes.

Neither kind is reference-counted: there is no lease to release. A child's
writes belong to the child, not its parent, and disposing the parent also
disposes every child.

```ts
const draft = myStore.scope("draft")
myStore.scope("draft") === draft // true

draft.dispose()
myStore.scope("draft") === draft // false: a new, empty scope
```

## Disposing stores

`dispose()` is terminal. It releases the Store's subscriptions and disposes its
descendant scopes. Every later operation on a disposed Store or any of its
scopes throws `StoreDisposedError`; calling `dispose()` again does nothing.
Create a new Store for later work.

Dispose short-lived stores, such as one per SSR request or background job, when
their work finishes. Valdres has no dispose hook, so release anything you keep
alongside a Store in the same place:

```ts
const requestStore = store()
const connection = openConnection()

try {
    return await renderRequest(requestStore, connection)
} finally {
    requestStore.dispose()
    connection.close()
}
```
