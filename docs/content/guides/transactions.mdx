# Transactions

Transactions let you update multiple atoms at once. Subscribers and selectors only re-evaluate after all updates are applied — never in an intermediate state.

## The problem

Without transactions, each `set` call immediately notifies subscribers:

```ts
import { atom, selector, store } from "valdres"

const firstName = atom("John")
const lastName = atom("Doe")
const fullName = selector(get => `${get(firstName)} ${get(lastName)}`)

const myStore = store()

// Two separate updates — subscribers fire twice
// After first set: fullName = "Jane Doe"
// After second set: fullName = "Jane Smith"
myStore.set(firstName, "Jane")
myStore.set(lastName, "Smith")
```

If a component is subscribed to `fullName`, it briefly shows "Jane Doe" before settling on "Jane Smith". That intermediate state may cause flickers or unnecessary work.

## The solution

Wrap related updates in `store.txn()`:

```ts
myStore.txn(tx => {
    tx.set(firstName, "Jane")
    tx.set(lastName, "Smith")
    // Nothing fires until here
})
// Now subscribers fire once with fullName = "Jane Smith"
```

## Synchronous callbacks

Transaction callbacks must be synchronous. Returning a Promise or other
thenable throws `InvalidTransactionCallbackResultError` and commits nothing,
because writes after an `await` cannot be part of the same atomic commit. Atom
values must be synchronous too. Perform asynchronous work before the
transaction, then apply its result synchronously:

```ts
const user = await fetchUser()

myStore.txn(tx => {
    tx.set(userAtom, user)
    tx.set(statusAtom, "ready")
})
```

## Atomic lifecycle

Valdres owns the transaction lifecycle. The callback receives a cursor with
`get`, `set`, `update`, `reset`, `delete`, `scope`, and the experimental
[`resetAll`](/react/store#resetting-a-scope-resetall), but no `commit()`
method or backing store data. Returning successfully commits once and hands
back the callback's return value; throwing discards every staged write:

```ts
myStore.txn(tx => {
    tx.set(statusAtom, "saving")
    throw new Error("save failed")
})

// statusAtom was not changed
```

If an operation intentionally needs multiple publish points, use separate
`store.txn()` calls. Each call is an explicit atomic boundary. Work deferred
from inside a callback, for example with `queueMicrotask` or a promise
continuation that starts a new transaction, is such a separate operation: it is
not part of the original atomic update, and subscribers will have seen the
state in between.

## Use the cursor

While the callback runs, Store operations captured from outside it throw
`TransactionPhaseError`. This applies to every Store from the same Valdres
runtime: the Store running the transaction, its scopes, and unrelated Stores
in other trees. Read and write through the cursor, and reach scopes of the same
tree with `tx.scope`:

```ts
myStore.txn(tx => {
    const name = tx.get(firstName) // not myStore.get(firstName)
    tx.scope("draft").set(firstName, name)
})
```

A transaction cannot write a Store in another tree. Run a separate transaction
on that Store after this one returns.

## Updater functions

As outside a transaction, `set` stores a value and `update` calls an updater
with the current staged value:

```ts
const countA = atom(0)
const countB = atom(0)

myStore.txn(tx => {
    tx.update(countA, prev => prev + 1)
    tx.update(countB, prev => prev + 10)
    tx.set(countA, 100) // stores 100
})
```

Transaction writes return `undefined`.

## Notification failures

Subscribers run after the transaction commits. If one throws, the remaining
subscribers still run, then `txn` throws a `SubscriberNotificationError` whose
`committed` property is `true`. The transaction's writes are already applied, so
do not run it again; see
[Notification failures](/react/store#notification-failures).

## When to use transactions

**Use transactions when:**
- Updating multiple related atoms that feed into the same selector
- Moving items between collections (remove from one, add to another)
- Resetting a form (clear all fields at once)
- Any operation where intermediate state would be wrong or confusing

**You don't need transactions when:**
- Updating a single atom
- Updates are unrelated and independent
- Intermediate states are acceptable

## Real-world example: drag and drop

When an item is dragged from one list to another, you need to remove it from the source and add it to the target atomically:

```ts
import { atom, family, store } from "valdres"

const listItemsAtom = family((listId: string) => atom<string[]>([]))

const myStore = store()

function moveItem(itemId: string, fromListId: string, toListId: string) {
    myStore.txn(tx => {
        tx.update(listItemsAtom(fromListId), ids =>
            ids.filter(id => id !== itemId),
        )
        tx.update(listItemsAtom(toListId), ids => [...ids, itemId])
    })
    // Components subscribed to either list update once
    // The item is never "missing" from both lists
}
```

## Performance

Transactions aren't just about correctness — they're a performance optimization. Without them, a subscribed selector depending on 10 atoms would recompute 10 times during a bulk update. With a transaction, it recomputes once.

```ts
const atoms = Array.from({ length: 100 }, () => atom(0))
const sum = selector(get => atoms.reduce((acc, a) => acc + get(a), 0))
myStore.sub(sum, () => render(myStore.get(sum)))

// Without txn: sum recomputes 100 times
atoms.forEach(a => myStore.set(a, 1))

// With txn: sum recomputes once
myStore.txn(tx => {
    atoms.forEach(a => tx.set(a, 1))
})
```
